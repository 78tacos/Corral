## 1. Build, run, publish

**You need:** the .NET 10 SDK (a Windows desktop workload is included), Windows 10/11 x64, and, only for the
installer, [Inno Setup 6](https://jrsoftware.org/isinfo.php) (`winget install JRSoftware.InnoSetup`).

```
dotnet build                 # Debug build into bin\Debug\net10.0-windows
dotnet run                   # build and run
dotnet run -- --config C:\temp\test.json    # run against a throwaway settings file
```

`Corral.csproj` targets `net10.0-windows` with WPF **and** Windows Forms (Forms is used only for the tray
icon, color dialog and `Screen` APIs). `ImplicitUsings` is deliberately **off**: with both UI frameworks
referenced, implicit usings would make names like `Application`, `Color` and `Point` ambiguous.
`WPF0001` is suppressed because `ThemeMode="System"` (the Fluent theme) is still marked experimental.

**Publish** (what the installer packages):

```
dotnet publish -c Release -r win-x64 --self-contained false -p:PublishSingleFile=true -p:DebugType=none -o dist
```

This produces a ~0.5 MB framework-dependent single file, `dist\Corral.exe`. The .NET 10 Desktop Runtime must be
present on the target machine.

> Only one Corral can run per Windows session (a named mutex). Close the installed copy (tray -> Exit) before
> running a debug build, or it will start and immediately exit.

## 2. Source map

| File | Responsibility |
|---|---|
| `App.xaml`, `App.xaml.cs` | Entry point. Single-instance mutex, `--config` and `--quit` switches, global exception handlers, creates `FenceManager` and `TrayController`, listens for the quit event. `ShutdownMode` is `OnExplicitShutdown` (no main window). |
| `FenceManager.cs` | Owns every `FenceWindow`, the `AppConfig`, and the debounced save. Creating/removing fences, snapping, desktop import ("organize"), desktop-icon visibility, tint management, start-with-Windows, keep-on-screen. Also defines `FenceColors`. |

## 3. Architecture

```
                       App (single instance, quit event)
                                   |
           +-----------------------+------------------------+
           |                       |                        |
     TrayController         FenceManager              DesktopClickWatcher
     (NotifyIcon, menu)   (settings, fences,           (WH_MOUSE_LL hook,
           |               snapping, save)               UIA icon test)
           |                  |        |                       |
           +---- calls ------>+        |                       |
                                       | owns                  |
                              +--------+---------+             |
                              |  FenceWindow x N |<--toggle----+
                              |  (WPF window per |
                              |   fence)         |
                              +----+--------+----+
                                   |        |
                          ShellIcons      Native (Win32)
                         (STA thread)
```

Data flow for a typical change (say, the user picks a color):

1. A menu click in `FenceWindow` or `TrayController` calls a method on `FenceManager`
   (`SetFenceTint` / `SetDefaultTint`).
2. The manager mutates the model (`FenceData.Tint` or `AppConfig.Tint`), tells the affected window(s) to
   re-apply (`ApplyBackdrop`), and calls `RequestSave()`.
3. `RequestSave()` (re)starts a 500 ms timer. When it fires, `SaveNow()` snapshots each window's on-screen
   bounds into its model and writes `config.json` atomically.

There is **no binding to model objects** for fence geometry or settings: the models are plain data, the
windows are authoritative for what is on screen, and `CaptureBounds()` copies window state back to the model
just before saving. Only the item list uses WPF data binding (`ObservableCollection<FenceItem>`).

## 4. How the tricky parts work

### 4.1 Fences live on the desktop layer

A fence is an ordinary top-level WPF `Window` made to behave like part of the desktop:

- `WindowStyle=None`, `ShowInTaskbar=False`, `ShowActivated=False`.
- Extended styles `WS_EX_TOOLWINDOW | WS_EX_NOACTIVATE` are added in `OnSourceInitialized` (hides it from Alt-Tab,
  and stops it taking focus when clicked).
- The window hook answers `WM_MOUSEACTIVATE` with `MA_NOACTIVATE`.
- The hook also rewrites every `WM_WINDOWPOSCHANGING` that would change z-order so `hwndInsertAfter` is
  `HWND_BOTTOM`. Nothing (including WPF's own show/hide) can raise a fence above normal windows.

Fences are *not* children of the desktop (`WorkerW`/`Progman`). That would make them immune to being covered
but is fragile across Windows builds. The trade-off is documented under [known limits](#11-known-limits-and-ideas).

Because the window is never active, it never receives keyboard focus. Anything that needs typing (renaming) uses
a separate normal dialog (`InputDialog`).

### 4.2 The blurred, tinted look

`Native.ApplyGlass` does four things:

1. `DwmSetWindowAttribute(33, 2)` rounds the corners on Windows 11 (no-op elsewhere).
2. `DwmSetWindowAttribute(34, COLOR_NONE)` removes the DWM border (the XAML `Border` draws a faint one instead).
3. `DwmExtendFrameIntoClientArea` with `-1` margins, so transparent pixels are composed by DWM.
4. `SetWindowCompositionAttribute` with an `ACCENT_ENABLE_ACRYLICBLURBEHIND` policy. The gradient color is
   `AABBGGRR`: the tint plus an alpha from the *Background* setting (`Opacity` 0-100 mapped to 0-255).

The window itself has `Background="Transparent"` and `HwndSource.CompositionTarget.BackgroundColor` is set to
transparent, which is what lets the acrylic show through. `SetWindowCompositionAttribute` is undocumented, so
it could change in a future Windows build, but it is widely used. It was chosen over the documented system
backdrop types because fences are never the active window, and the blur held up reliably in that state during
testing (the documented backdrops are designed to fall back to a flat color for inactive windows).

The tint is `FenceData.Tint ?? AppConfig.Tint`.

### 4.3 Coordinates are physical pixels

All stored geometry (`X`, `Y`, `Width`, `Height`) is in **physical screen pixels** on the virtual desktop,
not WPF device-independent units. Reading and writing uses `GetWindowRect` / `SetWindowPos` directly, which
avoids per-monitor DPI conversion bugs and makes multi-monitor layouts behave. Anything measured in XAML units
(minimum sizes, the rolled-up height) is multiplied by `VisualTreeHelper.GetDpi(this).DpiScaleX` first.

### 4.4 Move and resize

WPF's `DragMove` and resize borders are not used, because we need snapping and pixel control:

- The title bar and eight transparent "grip" rectangles (edges 5 px, corners 10 px, top 3 px) start a drag with a
  string mode: `"M"` for move, otherwise letters `L R T B` (e.g. `"BR"`).
- On mouse down: capture the mouse, record `GetCursorPos` and the window rect.
- On mouse move: compute the new rect from the cursor delta, clamp to the minimum size, pass it through
  `FenceManager.Snap`, and apply with `SetWindowPos`.
- On mouse up: release capture and `CaptureBounds()` (which requests a save).

**Snapping** (`FenceManager.Snap`): collect candidate x-lines and y-lines from the monitor's work area and from
every other visible fence. For the moving left edge the candidates are other fences' left edges and
*right edge + gap*; for the right edge, other fences' right edges and *left edge - gap* (and likewise top/bottom).
Within a 10 px threshold the nearest candidate wins, separately per axis. For a move both edges compete and the
closer wins; for a resize only the edges being dragged snap. Threshold and gap scale with DPI.

### 4.5 Roll-up and peek

`FenceData.Height` always holds the *expanded* height. Rolling up just sets the window height to the title row
(`RolledHeightDip`, 28 units); the model keeps the full height so unrolling restores it.

Peek is a transient flag (`_peeking`) that is not saved. On `MouseEnter` a rolled-up fence with peek enabled
expands; on `MouseLeave` a 350 ms timer collapses it unless the mouse has come back, a context menu is open,
or an item drag is in progress. `CaptureBounds` does not overwrite `Height` while rolled up or peeking.

### 4.6 Items, drag and drop

`FenceItem` wraps a path. The item list is a `ListBox` with extended selection and a `WrapPanel`.

**Items are adopted on the way in.** Every route that puts a path into a fence (a drop from outside,
`Organize desktop`, and the one-time upgrade in `AdoptExistingShortcuts`) passes it through
`LinkStore.Adopt(source, alreadyInFence)`. For a shortcut (`.lnk`, `.url`, `.appref-ms`) that returns the path of a
**private copy** in `%APPDATA%\Corral\Links` (the copy is made once; an identical shortcut already in the fence is
reused, name clashes become `Name (2).lnk`), and `FenceData.Items` stores the copy's path. For anything else, or if the
copy fails, it returns the original path unchanged. The fence therefore never depends on the original shortcut,
and a real file or folder remains a reference. Moving an item between fences keeps the same stored path.

**Items are discarded on the way out.** `FenceWindow.RemovePaths(paths, discard: true)` and
`FenceManager.RemoveFence` call `FenceManager.DiscardIfUnused`, which sends a stored copy to the Recycle Bin
(`Microsoft.VisualBasic.FileIO`, `SendToRecycleBin`) only if no other fence refers to it and only if the path is inside
the store. `TransferItems` passes `discard: false` so copies move with their items. `LinkStore.Recycle` is a
replaceable delegate so tests do not touch the real Recycle Bin.

**Starting a drag** (`List_PreviewMouseMove`): after the system drag threshold, the selected items are packaged
into a `DataObject` containing `DataFormats.FileDrop` (so Explorer and other apps understand it), and
`FenceManager.CurrentDrag` is set to a `DragPayload(sourceWindow, paths)`. Allowed effects are
`Copy | Link` only: **never `Move`**, so dropping onto a folder in Explorer can never move the user's real
files.

**Dropping** (`Fence_Drop`): `CurrentDrag != null` means the drag started in one of our own fences. Same fence:
`MoveWithin` reorders. Different fence: `FenceManager.TransferItems` adds to the target and removes from the
source (unless the source is a portal, which is copy-only). Otherwise it is a file drop from outside, and the
paths are added by reference. Portals reject all drops.

The drop position is the index of the item under the cursor, `+1` if the cursor is in its right half.
`MoveWithin` removes the dragged items first and adjusts the insert index by how many of them were before it.

### 4.7 Icons and thumbnails

`ShellIcons` runs one background thread in the **STA** apartment (shell COM objects require it) fed by a
`BlockingCollection`. For each request it:

1. `SHCreateItemFromParsingName` to get an `IShellItemImageFactory`.
2. `GetImage(size, flags)` with `SIIGBF_ICONONLY` for everything **except** a small list of image/video/PDF
   extensions, which allow real thumbnails (this is what the desktop does).
3. Reads the `HBITMAP` into top-down 32-bit BGRA with `GetDIBits` (avoids guessing orientation).
4. If the bitmap has no alpha at all, sets alpha to 255. If it has alpha, treats the pixels as premultiplied
   (`PixelFormats.Pbgra32`).
5. Freezes the `BitmapSource` (cross-thread safe), caches it by `(path, size)`, and completes the `Task`.

`FenceItem` awaits that task on the UI thread and raises `PropertyChanged`. The requested size is
`ceil(IconSize * dpiScale)` so icons are crisp on high-DPI screens. Display names come from `SHGetFileInfo` with
`SHGFI_DISPLAYNAME`, so they respect "hide file extensions".

### 4.8 Folder portals

When `FenceData.PortalPath` is set, `CurrentPaths()` enumerates the folder (folders first, then files, case-
insensitive name order, hidden/system excluded) instead of using `Items`. A `FileSystemWatcher` raises
created/deleted/changed/renamed events; a 300 ms timer coalesces bursts into one `ReloadItems()`.

### 4.9 Hiding the desktop icons

The desktop icons are a `SysListView32` inside `SHELLDLL_DefView`, which is a child of `Progman` or, after
the wallpaper-slideshow reshuffle, of a `WorkerW`. `Native.FindDesktopListView` tries `Progman` first, then
enumerates top-level windows. Hiding is `ShowWindow(listView, SW_HIDE)`; showing is `SW_SHOW`.

The desired visibility is a pure function in `FenceManager.ApplyDesktopIcons`:

```
hidden = fencesVisible ? Config.HideDesktopIcons : _cleanDesktop
```

`_cleanDesktop` is set only when fences were hidden *by a desktop double-click* while
`Config.DoubleClickHidesIcons` is on. `Shutdown()` always makes the icons visible again, and so does the
unhandled-exception handler in `App`.

### 4.10 Double-click the desktop

`DesktopClickWatcher` installs a `WH_MOUSE_LL` hook on the UI thread (which has a message loop). The delegate
is stored in a field so the garbage collector cannot free it while Windows still holds the pointer.

In the callback, for `WM_LBUTTONDOWN` only:

1. `Native.IsDesktopSurface(point)`: `WindowFromPoint` then the window class. True for `Progman`, `WorkerW`,
   `SHELLDLL_DefView`, or a `SysListView32` whose parent is `SHELLDLL_DefView`.
2. Compare with the previous desktop click: within `GetDoubleClickTime`, and within half of
   `SM_CXDOUBLECLK` / `SM_CYDOUBLECLK`. If both clicks were on the desktop, it is a double-click.
3. The callback itself stays cheap. The question "is that an icon?" is answered on a thread-pool thread with
   **UI Automation** (`AutomationElement.FromPoint`): a `ListItem` is an icon. Any failure is treated as
   "icon", so the feature fails safe (it does nothing) rather than hiding fences on a real icon double-click.
4. If it is empty desktop, `FenceManager.ToggleFencesVisible(fromDesktopClick: true)` runs on the UI thread.

If the desktop icons are themselves hidden, the click lands on `Progman`/`WorkerW` and UIA reports a pane, so
it still works.

### 4.11 Single instance and `--quit`

`App.OnStartup` creates a named mutex. A second launch exits quietly, *unless* it was started with `--quit`, in
which case it first signals a named `EventWaitHandle` (`Corral.Quit`) and then exits. The first instance has a
background thread waiting on that event; when signalled it runs the normal exit path
(`TrayController.Dispose`, `FenceManager.Shutdown`, `Shutdown()`), which saves settings and restores the icons.
The installer uses this instead of killing the process.

### 4.12 Persistence

- `ConfigStore.Save` writes to `config.json.tmp` then `File.Move(..., overwrite: true)`, so a crash mid-write
  cannot truncate the real file.
- `ConfigStore.Load` catches any exception, copies the unreadable file to `config.json.bad`, logs the reason and
  starts with defaults.
- Saves are debounced by 500 ms; `Shutdown()` forces one.
- `FenceManager.KeepOnScreen` runs at startup and on `SystemEvents.DisplaySettingsChanged`, and moves any fence
  that intersects no monitor's work area back onto the primary one.

### 4.13 Organize desktop

`GetDesktopEntries` lists the user and public desktops (skipping hidden/system files, `desktop.ini`, and paths
already in any fence). `OrganizeDesktop` groups them with `Categorise` (extension tables at the top of that
region of `FenceManager.cs`), then lays out one fence per group left-to-right, wrapping to a new row at the
right edge, with width from a column count of roughly `sqrt(count * 1.6)` clamped to 3-6 and height capped at
five rows. Shortcuts go through `LinkStore.Adopt`, so the new fences hold private copies (the originals stay on
the desktop). The tray controller confirms with the user and then enables *Hide desktop icons*.

## 5. Configuration file reference

Location: `%APPDATA%\Corral\config.json` (or the path given by `--config`). UTF-8 JSON, indented. Unknown
properties are ignored; missing ones take the defaults below.

### Top level (`AppConfig`)

| Property | Type | Default | Meaning |
|---|---|---|---|
| `Locked` | bool | `false` | Block moving and resizing fences |
| `HideDesktopIcons` | bool | `false` | Hide the real desktop icons while fences are visible |
| `SnapToEdges` | bool | `true` | Snap to work-area edges and other fences |
| `PeekOnHover` | bool | `true` | Rolled-up fences open while hovered |
| `DoubleClickDesktop` | bool | `true` | Double-click empty desktop toggles the fences |
| `DoubleClickHidesIcons` | bool | `false` | That double-click also hides the real icons |
| `Opacity` | int 0-100 | `55` | Tint strength over the blur (menu presets: 25, 40, 55, 75, 95) |
| `Tint` | string `#RRGGBB` | `#12141A` | Default fence color |
| `Fences` | array | `[]` | The fences, in creation order |

### Each fence (`FenceData`)

| Property | Type | Default | Meaning |
|---|---|---|---|
| `Id` | string | new GUID | Unique id (not currently used for lookups) |
| `Title` | string | `New Fence` | Title bar text |
| `X`, `Y` | int | 0 | Top-left, **physical pixels**, virtual-desktop coordinates |
| `Width`, `Height` | int | 320, 240 | **Physical pixels**. `Height` is the *expanded* height |
| `RolledUp` | bool | `false` | Collapsed to the title bar |
| `IconSize` | int | `48` | 32, 48 or 64 |
| `Tint` | string or null | `null` | Per-fence color; `null` uses the top-level `Tint` |
| `PortalPath` | string or null | `null` | If set, the fence mirrors this folder and `Items` is ignored |
| `Items` | string[] | `[]` | Full paths of the items, in display order. Shortcuts point into `<config dir>\Links\`; files and folders point at their real location |

Example:

```json
{
  "Locked": false,
  "HideDesktopIcons": true,
  "Opacity": 55,
  "Tint": "#12141A",
  "Fences": [
    {
      "Title": "Programs",
      "X": 120, "Y": 80, "Width": 480, "Height": 300,
      "IconSize": 48,
      "Tint": "#1B4FB8",
      "Items": [ "C:\\Windows\\notepad.exe", "C:\\Windows\\System32\\calc.exe" ]
    },
    {
      "Title": "Downloads",
      "X": 640, "Y": 80, "Width": 420, "Height": 300,
      "PortalPath": "C:\\Users\\me\\Downloads"
    }
  ]
}
```

Edit the file only while Corral is not running (it rewrites the file on changes and on exit).

### Other state

| What | Where |
|---|---|
| Shortcut copies | `Links\` next to `config.json`. Corral's private copies of shortcuts; `config.json` points into it, so back them up together |
| Log | `corral.log` next to `config.json`. Unhandled exceptions, failed saves, icon failures |
| Start with Windows | `HKCU\Software\Microsoft\Windows\CurrentVersion\Run`, value `Corral` = quoted exe path |
| Installer uninstall record | `HKCU\...\Uninstall\{5F1B2C4E-7A3D-4E8B-9C21-6D0A8B7E3F54}_is1` (per-user install) |

## 7. Installer and releases

The installer is built with **Inno Setup 6** from `installer\Corral.iss`.

```
pwsh installer\build.ps1
```

`build.ps1`:

1. Finds `ISCC.exe` (PATH, then the usual install folders; throws a helpful message if missing).
2. Reads the version from `<Version>` in `Corral.csproj`.
3. Deletes `dist\` and publishes the app into it (single-file, framework-dependent, no pdb).
4. Compiles `Corral.iss` with `/DAppVersion=<version>` into `installer\Output\Corral-Setup-<version>.exe`.

### What the installer script does

- **Per-user by default** (`PrivilegesRequired=lowest`, with the all-users choice offered by the wizard).
  Install folder `{autopf}\Corral`.
- 64-bit only (`ArchitecturesAllowed=x64compatible`), Windows 10 or later.
- **Runtime check** in `InitializeSetup`: looks for `Program Files\dotnet\shared\Microsoft.WindowsDesktop.App\10.*`.
  If absent (and not a silent install) it offers: open the download page and cancel, install anyway, or cancel.
- **Task** `startup` writes `HKCU\...\Run\Corral`, the same value the app's *Start with Windows* item writes.
- **Closing a running copy** (`PrepareToInstall` and `InitializeUninstall`): runs `Corral.exe --quit`, waits up
  to ~5 s for the process to disappear, and only then falls back to `taskkill /F`. `CloseApplications=no`, so
  Restart Manager does not force-close it.
- **Uninstall** removes files, the Start menu entries, and the `Run` value (even if it was set from the app's
  own menu). It then asks whether to delete `%APPDATA%\Corral`; the default is No. Silent uninstall never
  deletes it.
- Script-friendly switches: `/VERYSILENT /SUPPRESSMSGBOXES /NORESTART /DIR="..." /TASKS=startup`.

### Release checklist

1. Bump `<Version>` in `Corral.csproj`.
2. Add an entry to `CHANGELOG.md`.
3. Run the tests (`dotnet run --project tests\LinkStoreTests`) and build and run once; check the tray menu and a fence.
4. `pwsh installer\build.ps1`.
5. Test the installer on a **clean machine or VM** (see the warning in [section 8](#8-developer-scripts)).
6. Publish `installer\Output\Corral-Setup-<version>.exe`.

**Never change `AppId`** in `Corral.iss`. Windows and Inno use it to recognise an existing install; changing it
makes upgrades install side by side instead of over the old version.

**Signing.** The installer and exe are unsigned, so SmartScreen warns on first run. To sign, add a
`SignTool=` definition to `Corral.iss` and sign `dist\Corral.exe` before compiling.

**Self-contained alternative.** To remove the runtime requirement, publish with `--self-contained true` (do not enable
trimming; WPF does not support it), remove the runtime check from `Corral.iss`, and expect a much larger
installer (tens of megabytes).

## 8. Developer scripts

All live in `tools\` or `installer\`. They are PowerShell 7 and are meant for the developer's machine.

| Script | Purpose | Side effects to know about |
|---|---|---|
| `tools\snap.ps1 -Exe <exe> -OutDir <dir>` | Writes a test config (four fences: colored, rolled-up, a portal), launches Corral with it, and saves a PNG of each fence window using `PrintWindow`. Needs no changes to your real desktop | **Stops every running Corral** first (single-instance rule), including your installed copy. Restart it afterwards |
| `tools\dblclick-test.ps1 -OutDir <dir>` | Minimizes all windows, double-clicks empty desktop twice, takes a screenshot after each. Verifies the toggle end to end | **Minimizes your windows and moves and clicks the mouse for a few seconds**, then restores them. Don't use the PC during the run. Default click point is `(1725, 690)` physical px; pass `-X`/`-Y` for another empty spot |
| `tools\make-icon.ps1` | Draws the icon in code and writes `Assets\corral.ico` (nine sizes, PNG-compressed) | Overwrites the icon. `-Preview file.png` also saves the 256 px image |
| `tools\icon-sheet.ps1 -Ico <ico> -Out <png>` | Renders the icon at 16-48 px, zoomed, on dark and light, to check legibility | None |
| `tests\LinkStoreTests` (run: `dotnet run --project tests\LinkStoreTests`) | 25 assertions on `LinkStore`: copy survives deleting the original, files/folders not copied, duplicate reuse, name collisions, read-only originals, discard safety, look-alike folder paths, copy-failure fallback | Uses a temp folder it deletes; never touches the real Recycle Bin |
| `tools\e2e-copy-test.ps1 -Exe <exe> -WorkDir <dir> [-RealConfig <config.json>]` | Runs the real app against a throwaway config: shortcut copied in at startup, original deleted, item survives a restart (screenshot). With `-RealConfig` it dry-runs the migration on a *copy* of that config | **Quits your running Corral** (gracefully) and starts it again at the end. Never modifies the real config or originals |
| `tools\check-docs.ps1` | Checks the Markdown docs: no stray control characters, every relative link resolves, every `#anchor` matches a heading. Run it after editing docs | None |
| `installer\build.ps1` | Publish and build the installer | Recreates `dist\` |
| `installer\test-installer.ps1 -Setup <exe> -WorkDir <dir>` | Silent end-to-end test: install, launch, `--quit`, upgrade over a running copy, uninstall; prints PASS/FAIL | See the warning below |

> **Warning: `test-installer.ps1` and a real install.** The test uses the real `AppId`. On a machine where Corral
> is installed it would replace, then delete, that install's uninstall entry and start-at-sign-in setting, leaving
> the program files orphaned. The script therefore **refuses to run** if the uninstall record exists, unless you
> pass `-Force`. Run it on a clean VM or after uninstalling.

Screenshot-based checks work because `PrintWindow` with `PW_RENDERFULLCONTENT` captures composed windows,
including the acrylic. The desktop double-click test cannot avoid being intrusive, because the mouse hook and
the real desktop are the things under test.

## 9. Common changes, step by step

### Add a color preset

Add a `("Name", "#RRGGBB")` tuple to `FenceColors.Presets` in `FenceManager.cs`. Both the fence menu and the tray
menu are built from that array, so nothing else changes. Keep it dark enough for white text.

### Add a transparency level

Add a `("Label", value)` pair to the array in `TrayController.Rebuild` (values are percentages 0-100). The
*checked* state matches the closest preset within 8 points.

### Add a tray option backed by a setting

1. Add a property to `AppConfig` in `Config.cs` (give it a default; old config files will simply use it).
2. Add a `SetXxx` method on `FenceManager` that assigns it and calls `RequestSave()`.
3. Add an `Add("Label", () => _mgr.SetXxx(!_mgr.Config.Xxx), _mgr.Config.Xxx);` line in `TrayController.Rebuild`.
4. Act on it where needed (the menu is rebuilt each time it opens, so checkmarks stay correct).
5. Document it in `docs\USER-GUIDE.md` (the menu reference tables) and in section 5 above.

### Add an item right-click command

Add `menu.Items.Add(Item("Label", () => ...))` in `FenceWindow.ShowItemMenu`. `selection` is the list of selected
`FenceItem`s; use `single` to gate commands that only make sense for one item.

### Add a fence-level command

Add it in `FenceWindow.ShowFenceMenu`. If it changes persisted state, route it through a `FenceManager` method (or
call `_mgr.RequestSave()`).

### Add a new item category to "Organize desktop"

Add the extension list and a branch in `FenceManager.Categorise`, and add the category name to the ordering array
in `OrganizeDesktop`.

### Change the icon

Edit the drawing code in `tools\make-icon.ps1`, run it, run `tools\icon-sheet.ps1` to check small sizes, rebuild.

## 10. Gotchas and lessons learned

- **WPF + WinForms together.** Keep `ImplicitUsings` off and fully qualify the few cross-framework names
  (`System.Windows.Forms.Screen`, `System.Drawing.Color`). `Microsoft.Win32.OpenFolderDialog` (WPF) is used for
  folder picking so no WinForms dialog is needed there; the color picker is the one WinForms dialog.
- **Keep P/Invoke in `Native.cs`.** It uses `DllImport` with `GetWindowLongPtrW`/`SetWindowLongPtrW`, so the build
  is x64 only (`PlatformTarget` is `x64`).
- **Hook delegates must be rooted.** `DesktopClickWatcher` keeps `_proc` in a field. A local delegate would be
  collected and the process would crash the next time Windows called it.
- **Never do slow work in a low-level hook callback.** Windows silently removes hooks that take too long. The UIA
  call is deliberately pushed to the thread pool.
- **Shell COM needs STA.** Icon extraction on the default thread-pool (MTA) is unreliable, so it has its own STA
  thread.
- **Alpha handling of shell bitmaps.** Folder icons from `GetImage` without `ICONONLY` came back as opaque
  thumbnail-style bitmaps (white boxes). Requesting icons only, except for known thumbnail types, fixed it.
- **Two `.lnk` files are never byte-identical.** Windows stamps each newly created shortcut with timestamps, so
  `LinkStore` only reuses a copy when the dropped file is byte-for-byte the same one (the same original dropped
  again). Do not try to dedupe by name alone; different shortcuts often share one.
- **`Remove` must not discard on a move.** Dragging an item between fences is "add to target, remove from source".
  Discarding at that point would delete the copy that just moved, which is why `RemovePaths` has a `discard` flag.
- **Screen coordinates differ between tools.** The app is per-monitor DPI aware; PowerShell 7 reports physical
  pixels too, so the helper scripts use the same coordinates. A DPI-unaware host would not.
- **`Window.Show()` re-raises z-order.** That is why the `WM_WINDOWPOSCHANGING` rewrite exists; hiding and showing
  fences (double-click) relies on it.
- **Testing the desktop double-click needs the real desktop.** There is no way to unit-test the hook; see
  `tools\dblclick-test.ps1`.

## 11. Known limits and ideas

**Limits**

- Fences are bottom-most top-level windows, not desktop children, so a maximized window covers them and
  Win+D behaviour depends on Explorer.
- Transparency strength is app-wide, not per fence.
- No multiple pages of fences, no search, and no keyboard navigation (a consequence of the no-activate window).
- The item context menu is a curated set, not the full Explorer menu with shell extensions.
- Geometry is stored in physical pixels, so a different resolution or scale needs manual re-arranging.
- Hidden desktop icons cannot be restored if the process is force-killed; a normal exit, an unhandled error,
  the installer and the uninstaller all restore them.
- The installer and exe are unsigned.

**Ideas**

- Per-fence transparency and title-bar styles.
- Multiple pages per fence, or a "tabbed" fence.
- Drop an item on the desktop to remove it from its fence.
- Real shell context menu via `IContextMenu`.
- Auto-organize rules (new desktop files land in the right fence automatically).
- Per-monitor layouts that follow the display configuration.
- Auto-update check.
